# QUALITY_SCORE.md — EquiSense 품질 루브릭

> 이 문서는 EquiSense의 모든 코드, 문서, API, 데이터 산출물의 품질을 객관적으로 평가하기 위한 루브릭입니다.
> PR 리뷰, 스프린트 종료 점검, 릴리스 게이트 판단에 활용합니다.
> 각 영역은 1~4점 척도로 평가하며, 전체 평균 **3.0점 이상**이어야 프로덕션 배포 승인을 받을 수 있습니다.

---

## 점수 척도 정의

| 점수 | 등급 | 의미 |
|------|------|------|
| 4 | **Excellent** | 기준을 완전히 충족하고, 팀 표준을 선도할 수 있는 수준 |
| 3 | **Meets Standard** | 기준을 충족하며 프로덕션 배포에 적합한 수준 |
| 2 | **Needs Improvement** | 부분적으로 충족하나 개선이 필요한 수준. 배포 전 수정 필요 |
| 1 | **Unacceptable** | 기준 미달. 즉시 재작업 필요, 배포 블로킹 |

---

## 영역 1: 코드 품질 (Code Quality) — 가중치 25%

### 1-1. 가독성 및 구조

**4점 (Excellent)**: 함수와 변수의 이름만으로 의도를 완전히 파악할 수 있으며, 복잡한 로직에는 인라인 주석과 docstring이 적절히 작성되어 있다. 단일 책임 원칙이 모든 함수와 클래스에서 준수되고, 함수 길이가 40줄을 초과하지 않는다.

**3점 (Meets Standard)**: 대부분의 이름이 명확하고, 주요 함수에 docstring이 존재한다. 일부 함수가 40~60줄 수준이지만 논리적으로 분리가 어려운 이유가 있다.

**2점 (Needs Improvement)**: 약어나 의미 없는 변수명(`data`, `tmp`, `x`)이 산재하며, docstring이 절반 이하의 함수에만 존재한다.

**1점 (Unacceptable)**: 코드 목적을 파악하기 위해 별도의 질의가 필요하다. 이름 규칙이 파일마다 다르고, 주석이 전혀 없다.

---

### 1-2. 오류 처리 및 방어 코드

**4점 (Excellent)**: 모든 외부 I/O(API 호출, DB 쿼리)에 예외 처리와 지수 백오프 재시도가 구현되어 있다. 오류 응답은 표준 스키마를 따르며 `request_id`를 포함하여 추적 가능하다.

**3점 (Meets Standard)**: 주요 외부 호출에 `try/except`가 적용되고, 에러 메시지가 클라이언트에 노출된다. 재시도 로직이 최소 1회 이상 구현되어 있다.

**2점 (Needs Improvement)**: 일부 경로에서 예외가 처리되지 않아 500 에러가 사용자에게 그대로 노출될 수 있다.

**1점 (Unacceptable)**: `except: pass` 또는 빈 예외 핸들러가 존재한다. 에러 스택 트레이스가 API 응답에 그대로 포함된다.

---

### 1-3. 테스트 커버리지

**4점 (Excellent)**: 핵심 비즈니스 로직 커버리지 90% 이상. 단위 테스트와 통합 테스트가 모두 존재하며, 엣지 케이스(빈 응답, API 타임아웃, 잘못된 입력)에 대한 테스트가 포함되어 있다.

**3점 (Meets Standard)**: 핵심 로직 커버리지 80% 이상. 해피 패스(happy path)와 주요 실패 케이스가 테스트된다. 외부 API는 모킹으로 격리된다.

**2점 (Needs Improvement)**: 커버리지 60~80%. 해피 패스만 테스트되며 실패 케이스가 누락되어 있다.

**1점 (Unacceptable)**: 커버리지 60% 미만, 또는 테스트 파일 자체가 존재하지 않는다.

---

## 영역 2: 아키텍처 준수 (Architecture Compliance) — 가중치 25%

### 2-1. Serverless 원칙 준수

**4점 (Excellent)**: 모든 Lambda 함수가 단일 책임을 가지며, 함수 간 직접 HTTP 호출이 없다. API Gateway 또는 SQS를 통한 올바른 통신 패턴만 사용된다.

**3점 (Meets Standard)**: 서버리스 원칙을 대체로 준수하나, 경미한 예외(예: 내부 유틸리티 함수의 직접 임포트)가 1~2건 존재하며 문서화되어 있다.

**2점 (Needs Improvement)**: Lambda 함수가 다른 Lambda를 직접 HTTP 호출하거나, 서버 상태(인스턴스 변수)에 비즈니스 데이터를 저장하는 패턴이 발견된다.

**1점 (Unacceptable)**: EC2 인스턴스, 컨테이너 기반 상시 서버가 도입되었거나, SQS 없이 무거운 작업이 동기 Lambda에서 처리되어 타임아웃 위험이 존재한다.

---

### 2-2. 비동기 작업 패턴

**4점 (Excellent)**: 모든 장기 실행 작업이 SQS → Worker Lambda 패턴으로 구현되고, 작업 상태가 `analysis_jobs` 테이블에서 `PENDING → PROCESSING → COMPLETED | FAILED`로 추적된다. 클라이언트는 202 응답 즉시 수신한다.

**3점 (Meets Standard)**: 비동기 패턴이 구현되어 있으나 상태 추적이 단순하거나(PENDING/DONE만), 폴링 간격이 최적화되지 않았다.

**2점 (Needs Improvement)**: 일부 장기 작업이 동기 Lambda에서 처리되어 타임아웃 위험이 있다. 클라이언트가 응답을 오래 기다린다.

**1점 (Unacceptable)**: 비동기 처리 패턴 자체가 구현되지 않았다. 사용자 요청이 Lambda 타임아웃(최대 15분)을 초과할 가능성이 있다.

---

### 2-3. 캐싱 전략 구현

**4점 (Excellent)**: 재무제표(24h), 주가(15분/24h), 뉴스(1h)의 계층적 TTL이 모두 Upstash Redis에 구현되어 있다. Cache-hit ratio가 90% 이상으로 외부 API 비용이 최소화된다.

**3점 (Meets Standard)**: 주요 외부 API 응답이 캐싱되고 있으며, TTL이 합리적으로 설정되어 있다. 캐시 미스 시 외부 API 폴백이 정상 작동한다.

**2점 (Needs Improvement)**: 캐싱이 일부 엔드포인트에만 적용되거나, TTL 설정이 너무 짧아(1분 미만) 캐싱 효과가 미미하다.

**1점 (Unacceptable)**: 외부 API 응답을 캐싱하지 않아 요청마다 API를 직접 호출한다. Rate Limit 초과 위험이 있다.

---

## 영역 3: API 설계 품질 (API Design) — 가중치 20%

### 3-1. RESTful 설계 원칙

**4점 (Excellent)**: HTTP 메서드(GET/POST/PUT/DELETE)가 의미에 맞게 사용되고, 리소스 경로가 명사로 구성된다(`/companies/{ticker}/fundamentals`). 응답 상태 코드가 정확하게 사용된다(200, 201, 202, 400, 401, 404, 500).

**3점 (Meets Standard)**: 대부분의 엔드포인트가 RESTful 관행을 따르며, 상태 코드 사용이 적절하다. 경미한 경로 명명 불일치가 있을 수 있다.

**2점 (Needs Improvement)**: 모든 것을 POST로 처리하거나, 동사를 경로에 포함(`/getCompanyData`)하는 패턴이 발견된다.

**1점 (Unacceptable)**: API 설계 원칙이 없으며, 상태 코드가 무작위로 사용된다(성공에도 500 반환 등).

---

### 3-2. 입력 검증 및 스키마

**4점 (Excellent)**: 모든 요청 파라미터가 Pydantic 모델(Python) 또는 Zod(TypeScript)로 검증된다. 유효하지 않은 입력에 대해 필드별 오류 메시지가 반환된다.

**3점 (Meets Standard)**: 주요 파라미터(ticker, date)가 정규식 또는 Pydantic으로 검증된다. 오류 메시지가 충분히 명확하다.

**2점 (Needs Improvement)**: 입력 검증이 일부 엔드포인트에만 존재하며, SQL 인젝션 또는 XSS 벡터가 잠재적으로 존재한다.

**1점 (Unacceptable)**: 입력 검증이 전혀 없어 비정상적인 입력이 DB 쿼리에 그대로 사용된다.

---

## 영역 4: 보안 (Security) — 가중치 15%

> 상세 보안 규칙은 `SECURITY.md`를 참조합니다.

### 4-1. 시크릿 관리

**4점 (Excellent)**: 모든 시크릿이 AWS Secrets Manager에 저장되고, Lambda 실행 시 동적으로 조회된다. 소스 코드 및 Git 히스토리에 시크릿이 존재하지 않는다(`git-secrets` 스캔 통과).

**3점 (Meets Standard)**: 시크릿이 환경 변수로 관리되며, 코드에 하드코딩되지 않는다. `.env` 파일이 `.gitignore`에 포함되어 있다.

**2점 (Needs Improvement)**: 테스트 또는 개발 환경에서 시크릿이 코드에 주석으로 남아 있거나, README에 예시 키가 실제 키처럼 보인다.

**1점 (Unacceptable)**: API 키, DB 비밀번호가 소스 코드에 직접 포함되어 Git에 커밋되어 있다. 즉시 키 로테이션 필요.

---

### 4-2. IAM 최소 권한

**4점 (Excellent)**: 각 Lambda 함수의 IAM 역할이 해당 함수가 실제로 사용하는 리소스와 작업만 허용한다. `*` 와일드카드 Action 또는 Resource가 존재하지 않는다.

**3점 (Meets Standard)**: 주요 함수의 IAM 역할이 필요 최소한으로 설정되어 있다. 일부 관리 편의를 위한 광범위한 권한이 있으나 문서화되어 있다.

**1점 (Unacceptable)**: Lambda 함수에 `AdministratorAccess` 또는 `*:*` 권한이 부여되어 있다.

---

## 영역 5: 문서화 (Documentation) — 가중치 15%

### 5-1. 코드 내 문서화

**4점 (Excellent)**: 모든 공개 함수에 docstring이 있으며, 파라미터 타입·반환값·예외가 명시된다. 복잡한 알고리즘(해자 점수 계산, RAG 청킹 로직)에는 설계 의도를 설명하는 주석이 포함된다.

**3점 (Meets Standard)**: 핵심 함수에 docstring이 존재하고, 코드만으로 이해하기 어려운 부분에 주석이 달려 있다.

**2점 (Needs Improvement)**: Docstring이 일부 함수에만 존재하거나, 파라미터 타입 정보가 누락되어 있다.

**1점 (Unacceptable)**: 코드 내 주석과 docstring이 전혀 없어 작성자 외에는 이해하기 어렵다.

---

### 5-2. 설계 문서 최신성

**4점 (Excellent)**: `design-docs/`, `product-specs/`, `exec-plans/`의 내용이 실제 구현과 일치하며, 변경사항 발생 시 48시간 이내에 문서가 업데이트된다.

**3점 (Meets Standard)**: 주요 설계 문서가 구현의 90% 이상을 반영하고 있다. 일부 마이너한 변경이 문서에 미반영될 수 있으나, 스프린트 종료 전 동기화된다.

**2점 (Needs Improvement)**: 문서와 구현 간 불일치가 20% 이상으로, 문서를 신뢰하기 어렵다.

**1점 (Unacceptable)**: 설계 문서가 초기 계획서 이후 한 번도 업데이트되지 않았다. 실제 구현과 다른 내용이 다수 포함되어 있다.

## 종합 점수 계산 및 릴리스 게이트

각 영역의 점수에 가중치를 곱하여 최종 점수를 산출합니다.

```
최종 점수 = (코드 품질 평균 × 0.25) + (아키텍처 준수 평균 × 0.25)
           + (API 설계 × 0.20) + (보안 × 0.15) + (문서화 × 0.15)
```

**릴리스 기준:**

| 최종 점수 | 판정 | 조치 |
|-----------|------|------|
| 3.5 이상 | ✅ SHIP | 프로덕션 배포 승인 |
| 3.0 ~ 3.49 | ⚠️ SHIP WITH NOTES | 배포 가능, 다음 스프린트 내 개선 항목 등록 |
| 2.0 ~ 2.99 | 🔴 HOLD | 주요 이슈 수정 후 재검토 |
| 2.0 미만 | ⛔ REJECT | 배포 불가. 전면 재작업 후 재검토 |

**즉시 배포 블로킹(점수 무관):**

보안 영역 4-1(시크릿 관리)에서 1점을 받은 경우, 최종 점수와 무관하게 즉시 배포가 차단됩니다. API 키 또는 자격증명이 Git에 노출된 것은 점수 시스템으로 완화할 수 없는 보안 사고입니다.
